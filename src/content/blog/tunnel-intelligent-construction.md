## 项目背景

这个项目面向隧道施工过程中的几个实际环节：工程基础资料管理、爆破设计、围岩分析、超欠挖检测和施工数据展示。

它不是单独做某一个算法页面，而是先把工程对象管理起来，再把检测、计算和分析结果挂回对应的施工位置。项目、隧道、工作面、里程段构成了整套系统的主线，后面的爆破设计、围岩识别和超欠挖任务都围绕这条主线展开。

从使用场景来看，现场或管理人员不需要在多个系统之间反复找数据。选中一个里程段后，可以继续查看这一段的围岩情况、爆破参数、检测任务和超欠挖结果；管理层则可以在项目或企业维度看到汇总数据。

## 工程数据是怎么组织的

隧道项目的数据如果只用一张“项目表”来管理，后续很难把施工状态和分析结果对应起来。这个项目将施工对象拆成了几个层级：

- 项目：记录线路、施工概况、建设周期和项目成员等基础信息。
- 隧道：记录隧道名称、长度、起止桩号、掘进方向、风险等级和施工单位等信息。
- 工作面：表示具体施工位置，关联施工区间、班组和责任人。
- 里程段：继续细分施工进度，也是围岩、爆破和超欠挖数据最终落点。

用户选择项目、隧道、工作面或里程段后，当前节点的 ID 会保存到状态管理中，基础信息、爆破设计、围岩识别和超欠挖页面会据此切换查询条件。这样每个业务模块都能明确知道自己正在处理哪一段工程数据。

## 系统里的几个主要功能

### 1. 工程基础信息

基础信息模块负责维护项目、隧道、工作面和里程段。项目树支持搜索、在建或已完工筛选、右键新增编辑等操作，基础信息页面则会随着所选节点切换到对应的管理视图。

这一层看起来是常规的增删改查，但它决定了后续数据是否能串起来。比如一份点云分析结果如果没有明确关联到工作面和里程段，后面无论做统计还是追溯，都会变得很麻烦。

### 2. 智能爆破设计

爆破设计模块不是只维护一组固定参数。它会结合隧道断面、围岩等级、钻孔方式、施工条件、曲线数据和保护对象等基础资料，形成一个可计算的设计参数集合。

前端页面分为总览和参数设计两个部分：

- 总览会按工作面汇总里程段的设计结果和炸药用量。
- 参数页可以查看和分组保存设计参数，也支持 Excel 导入、导出。
- 提交计算后，页面不会一直等待接口返回，而是拿到任务 ID 后轮询任务状态，再读取计算结果。
- 部分设计结果可以和第三方系统同步，避免人工重复录入。

后端接到计算请求后会生成任务 ID，将任务状态写入 Redis，并通过 RabbitMQ 投递到异步消费者。消费者调用外部计算服务，计算完成后将结果按任务 ID 缓存。这样的处理方式适合计算时间不稳定的场景，用户可以继续操作页面，也能看到任务是否还在执行、是否失败或已经完成。

### 3. 围岩智能识别

围岩判断直接影响爆破参数和施工风险控制。项目里围岩模块会保存抗压强度、完整性系数、地下水、结构面、初始应力等参数，同时关联掌子面图片和点云文件。

整个流程不是一次请求就结束，大致分成下面几步：

- 上传掌子面图片和相关资料。
- 发起点云生成任务。
- 根据结果进行点云裁剪。
- 调用第三方服务进行后续分析。
- 轮询任务状态，将最终的点云文件和分析结果归档到对象存储。

为了避免 Redis 过期或服务重启后丢失任务状态，关键状态不仅放在缓存里，也会回写到里程段相关表中。这样用户下次进入页面，仍然能知道这段围岩分析做到哪一步。

### 4. 超欠挖分析

超欠挖模块处理的是设计轮廓和实际开挖轮廓之间的差异。实际业务里会涉及 PLY 点云、DXF 设计轮廓、二维和三维结果文件，单个文件体积通常也比普通表单附件大得多。

前端支持大文件分片直传到 OSS，并在上传后同步给第三方服务处理。用户可以选择已有围岩分析的点云，也可以单独上传；任务完成后，页面会展示设计面积、实测面积、超挖和欠挖面积、方量及极值等指标。

这一块还加入了 Three.js 的点云预览。页面加载 PLY 文件后，可以旋转、平移、缩放，并通过裁剪平面查看局部区域。对这种结果来说，只展示几个数值不够，现场人员还需要能看到偏差大致出现在什么位置。

### 5. 检测结果与施工看板

系统还接入了检测云数据。检测结果页面可以按项目或地址筛选，查看检测摘要、综合等级、设备信息、测点明细，并下载原始文件。

看板分为项目和企业两个维度。项目看板更关注隧道数量、里程进度、围岩等级、爆破设计和超欠挖统计；企业看板则会聚合项目规模、区域、设备、人员和巡检等信息。前端使用 ECharts 等组件做图表展示，后端提供聚合接口，避免页面自己拼接大量明细数据。

## 前端是怎么做的

前端采用 Vue 3、TypeScript、Vite、Pinia 和 Naive UI，并在 RuoYi-Vue-Plus / Soybean Admin 的基础上做了业务扩展。

我觉得比较重要的不是页面数量，而是几个公共能力的复用：

- 项目树和里程段选择器作为公共业务组件，被多个模块共用。
- Pinia 保存当前工程节点、用户信息、路由、页签和主题等状态，刷新后仍能恢复当前选择。
- 路由和菜单使用后端动态下发的方式，登录后根据权限加载可访问页面。
- 请求层统一附带 Token、客户端标识和语言信息，对重复提交、401、二进制下载和接口加密做了集中处理。
- 大文件上传、OSS 文件选择、表格、字典和人员选择等都封装成了通用组件，业务页面不需要反复处理这些细节。

围岩和超欠挖页面的交互会更复杂一些。它们都包含任务轮询、状态提示和结果回显；超欠挖还要处理点云文件的加载与三维交互。把这些状态拆清楚，比单纯把接口调用堆在页面里更重要，否则任务中断、页面刷新或第三方返回异常时会很难处理。

## 后端的职责

后端基于 Java 17、Spring Boot 3 和 RuoYi-Vue-Plus 构建，使用 MyBatis-Plus 管理数据访问。通用的认证、角色权限、菜单、文件、日志和对象存储能力由框架底座提供，隧道工程相关能力集中在独立业务模块中。

业务层主要做了几件事：

- 维护工程对象和施工基础参数。
- 为前端提供项目树、里程段、爆破、围岩、超欠挖和大屏接口。
- 对接外部爆破计算、围岩点云分析、检测云和 IoT 等服务。
- 使用 Redis 保存短期任务状态和第三方 Token。
- 使用 RabbitMQ 承接耗时计算、文件同步和结果入库，避免长时间占用 HTTP 请求。
- 通过 OSS 管理掌子面图片、点云、设计轮廓和分析结果文件。

比较典型的一条链路是：前端提交任务后立即得到任务 ID，后台异步调用外部服务，前端按间隔查询状态；任务成功后，后端将结果文件转存到 OSS，再把文件信息、指标和状态写回业务库。这样即使第三方服务响应慢，用户也不必一直停在加载页面。

## 这个项目里比较费时间的地方

### 文件不是普通附件

点云、DXF 和分析结果文件体积大，上传后还要被第三方服务读取。这里不能只依赖应用服务器转发文件，所以需要做 OSS 上传、临时文件下载、同步状态记录和失败后的清理处理。

### 第三方任务的状态不确定

爆破计算、点云处理和检测服务都不在本系统内部，接口成功返回不代表计算已经完成。项目里采用任务 ID、轮询、Redis 缓存、数据库状态回写和消息队列组合处理。它不一定能让任务更快完成，但能让任务过程可追踪，也方便排查问题。

### 工程数据需要能追溯

同一条隧道不同工作面、不同里程段的施工情况可能差异很大。把数据落到明确的工程层级，后面才能知道某个分析结果属于哪里，也才能做项目级汇总和趋势判断。

### 三维结果需要能看懂

超欠挖分析不仅要计算数值，还要让使用者看到点云和设计轮廓的差异。三维预览、裁剪和局部查看虽然增加了前端复杂度，但比只给一张表格更符合这类场景。

## 项目中已经具备和仍待完善的内容

从现有实现看，工程基础信息、智能爆破、围岩分析、超欠挖任务、检测云接入和看板已经形成了较完整的主流程。系统管理、动态权限、对象存储和第三方任务编排也为业务模块提供了支撑。

同时也能看到还有继续打磨的空间。例如地质雷达页面目前还是占位内容，围岩结果的一些详情和导出入口仍在完善中。对于这种工程型系统来说，后续重点不只是继续增加页面，更重要的是补齐任务失败后的处理、结果复核、数据版本和现场使用反馈。

## 总结

这个项目让我看到，隧道施工数字化并不是做一个填表后台，再接一个算法接口就结束了。真正需要处理的是工程对象、文件、任务、外部服务和结果展示之间的关系。

把项目、隧道、工作面和里程段这条线建立起来，再把爆破、围岩和超欠挖数据放回对应位置，系统才有机会从零散的工具，变成能服务施工过程的数据平台。后面的优化方向也比较明确：让任务状态更稳定、让结果更容易复核、让历史施工数据能真正被复用。
